# Dapr Kubernetes Operator

The `Dapr Kubernetes Operator` manages the lifecycle for Dapr and its components. 
The operator's goal is to automate the tasks required when operating a Dapr running in [Kubernetes Mode](https://docs.dapr.io/operations/hosting/kubernetes/).

## Installation

The `Dapr Kubernetes Operator` was created with the intention of running through the [Operator Lifecycle Manager][olm_home], 
specifically on [OpenShift 4][openshift_home]. This is where the operator shines most, as it leverages the powerful 
features built into the latest version of OpenShift.

That being said, the operator can be installed and provide the same functionality on any Kubernetes cluster. The 
following methods are provided for installing the operator.

### OpenShift

The operator is published as part of the built-in Community Operators in the Operator Hub on OpenShift 4. See the 
[OpenShift Install Guide][install_openshift] for more information on installing on the OpenShift platform.

### Operator Lifecycle Manager

Using the Operator Lifecycle Manager to install and manage the `Dapr Kubernetes Operator` is the preferred method. The operator 
is published to [operatorhub.io][operatorhub_link]. Following the installation process there should work for most OLM 
installations.

Look at the [OLM Install Guide][install_olm] for an example using this approach with minikube. 

### Manual Installation

The operator can be installed manually if desired.

> [!IMPORTANT]
> The manual installation method requires cluster credentials that provide the `cluster-admin` ClusterRole or equivalent.

The [Manual Installation Guide][install_manual] provides the steps needed to manually install the operator on any 
Kubernetes cluster.

## Usage

### Basic

The following example shows the most minimal valid manifest to create a new Dapr instance:

```yaml
apiVersion: operator.dapr.io/v1alpha1
kind: DaprInstance
metadata:
  name: "dapr-instance"
spec:
  values: {}
```

```yaml
# Deprecated, use DaprInstance instead
apiVersion: operator.dapr.io/v1alpha1
kind: DaprControlPlane
metadata:
  name: "dapr-control-plane"
spec:
  values: {}
```

The `DaprInstance` resource is a Kubernetes Custom Resource (CRD) that describes the desired state for a given Dapr instance and allows for the configuration of the components that make up the instance.

When the `Dapr Kubernetes Operator` sees a new `DaprInstance` resource, the Dapr components are provisioned using Kubernetes resources generated from the official [Dapr Helm Charts](https://github.com/dapr/helm-charts) and managed by the operator.
This means that the same configuration option that are available when [installing Dapr using Helm](https://docs.dapr.io/operations/hosting/kubernetes/kubernetes-deploy/#install-with-helm-advanced) can also be used to configure the `Dapr Kubernetes Operator`
When something changes on an existing `DaprInstance` resource or any resource generated by the operator, the operator works to reconfigure the cluster to ensure the actual state of the cluster matches the desired state.

> [!IMPORTANT]
> The operator expect that a single `DaprInstance` named `dapr-instance` and placed in the same namespace where the operator runs exists at a given point in time.
> Any additional `DaprInstance` resources will be moved to an `Error` state and ignored.

The `DaprInstance` Custom Resource consists of the following properties

| Name   | Default | Description                                                      |
|--------|---------|------------------------------------------------------------------|
| values | [Empty] | The [values][helm_configuration] passed into the Dapr Helm chart |
| chart  | [Empty] | The Dapr Helm chart to use instead of the chart in the operator. Fields: `repo` (default `https://dapr.github.io/helm-charts`), `name` (default `dapr`), `version`, and `secret` (the credentials for `repo`). See [Versions and Channels](#versions-and-channels). |

## Versions and Channels

Each operator release installs one Dapr version, and the operator version is equal to that Dapr version. For example, operator `1.19.1` installs Dapr 1.19.1. Releases up to `0.0.15` used a separate version number.

The operator is published to these OLM channels:

| Channel    | Content                                                                 |
|------------|-------------------------------------------------------------------------|
| `alpha`    | The default channel. It follows the newest Dapr minor version.          |
| `dapr-X.Y` | The releases for Dapr X.Y only. For example, `dapr-1.18` for Dapr 1.18. |

To stay on a Dapr minor version, set `spec.channel` in the `Subscription` to `dapr-X.Y`. OLM then upgrades the operator only to new releases for that minor version. After the switch, OLM upgrades the operator only if a release in the new channel replaces the installed version. For example, `0.0.14` (Dapr 1.18.4) upgrades in `dapr-1.18`. `0.0.15` (Dapr 1.19.0) stays on `0.0.15` in `dapr-1.18`, because no release in that channel replaces it.

With manual approval, the subscription can have an InstallPlan from the old channel that is not approved. OLM does not resolve the new channel while that InstallPlan is pending. Delete it, and OLM then creates an InstallPlan from the new channel.

To install a Dapr patch version without a new operator release, set `spec.chart.version` in the `DaprInstance`. The operator then loads that chart from `spec.chart.repo` instead of the chart that it contains. Use this only for a patch version of the Dapr minor version that the operator installs.

The operator does not compare `spec.chart.version` with its own chart, so the setting stays in force after an operator upgrade. Remove `spec.chart` when the installed operator release contains the Dapr version that you need.

```yaml
apiVersion: operator.dapr.io/v1alpha1
kind: DaprInstance
metadata:
  name: "dapr-instance"
spec:
  chart:
    version: "1.18.10"
  values: {}
```


Update `HELM_CHART_VERSION` in the `Makefile`, then run:

```bash
make update/dapr
```

### Release

A release is published when a change to the version in `helm-charts/dapr/Chart.yaml` reaches `main` or a `release-X.Y` branch, for example when the pull request with the output of `make update/dapr` merges. The release workflow publishes the operator image and the bundle, and for `main` also the catalog image. Then it creates the `v` tag and the GitHub release. It does nothing when the tag exists or when the chart version is a pre-release.

To publish a release by hand, push the `v*` tag. The workflow then creates the GitHub release, so do not create it yourself.

The release workflow checks the version and finds the place of the release in the OLM update graph:

- The tag is `v` and the version in `helm-charts/dapr/Chart.yaml`, for example `v1.19.1`. A pushed tag that does not match stops the release. Pre-releases are not published.
- The bundle replaces the previous `v*` tag in the history of the release commit. That tag must be lower than the new tag.
- A release from `main` goes to the `alpha` channel and to the `dapr-X.Y` channel. A release from another branch goes to the `dapr-X.Y` channel only.

`main` holds the newest Dapr minor version. To make patch releases for an older Dapr minor version:

1. Create the `release-X.Y` branch from the last release tag for that minor version.
2. Make sure that the branch has this release workflow. A tag from before this workflow, for example `v0.0.14`, has the old one: it publishes to `alpha` only and overwrites `kubernetes-operator-catalog:latest`. On such a branch, cherry-pick the changes to `.github/workflows/build-release.yml`, `.github/workflows/publish.yml`, `Makefile` and `hack/scripts/gen_bundle.sh` from `main` first.
3. Update the Dapr Helm chart on that branch with a pull request. The merge publishes the release.

Bring changes to a `release-X.Y` branch with cherry-picks. A merge from `main` adds newer tags to the history of the branch, and the release workflow then stops the release.

All bundles keep `alpha` as their default channel annotation. In the catalog, the bundle with the highest version sets the default channel of the package. The release workflow does not build the `kubernetes-operator-catalog` image for a tag that is not on `main`, because opm builds that image from the new bundle only.

OperatorHub.io and the OpenShift catalog do not get a release automatically. For each release, open a pull request that adds the bundle to `operators/dapr-kubernetes-operator/<version>/` in `k8s-operatorhub/community-operators` and in `redhat-openshift-ecosystem/community-operators-prod`.

### Run E2E Tests

The project uses end-to-end tests that run against a real Kubernetes cluster.

1. Create a Kind cluster:
   ```bash
   make test/e2e/kind/setup
   ```

2. Deploy the ingress controller:
   ```bash
   make deploy/e2e/ingress
   ```

3. Build and publish the operator image (using [ttl.sh](https://ttl.sh) as a temporary registry):
   ```bash
   export CONTAINER_IMAGE="ttl.sh/$(uuidgen | tr '[:upper:]' '[:lower:]'):1h"
   make docker/build docker/push
   ```

4. Deploy the operator:
   ```bash
   make deploy/e2e/controller
   ```

5. Build the test application:
   ```bash
   make test/e2e/app
   ```

6. Run the tests:
   ```bash
   make test/e2e/operator
   ```

7. Tear down the Kind cluster:
   ```bash
   make test/e2e/kind/teardown
   ```

### Run E2E OLM Tests

```bash
make deploy/e2e/olm
make test/e2e/olm
```
